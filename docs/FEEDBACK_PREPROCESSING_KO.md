## 0. 집단과 "적합 묶음"

결측 대치에는 두 가지 범위가 있습니다. 하나는 **대치 규칙(코드 사전·노선 중앙값)을 만든 묶음(적합 묶음)**이고, 다른 하나는 **수를 센 집단(분모)**입니다. 두 범위를 섞으면 숫자가 맞지 않습니다.

| 기호 | 집단(분모) | 행 수 | 적합 묶음 | 사용처 |
|---|---|---:|---|---|
| A | 원본 전체(라벨+미라벨) | 1,000,000 | A 자신 | 전처리 실험의 피처 생성(`rerun_all_phases.build_features(raw, …)`) |
| B | A 중 라벨 있음 | 255,001 | A | 전처리 10조건 비교·OOF 진단의 평가 집단 |
| C | 날짜 귀속 채택(라벨+미라벨) | 706,759 | C 자신 | 날씨 비교 러너의 피처 생성(`build_pair` → `runner.build_features(adopted, spec)`) |
| D | C 중 라벨 있음 | 180,332(지연 31,805) | C | 날씨 사용/미사용 비교의 평가 집단 |

- 근거: JSON `populations`. 라벨 판정은 `split_labeled`와 같은 규칙(`Delay`가 비어 있지 않음)입니다.
- A·B 행은 A 전체로 만든 사전·중앙값으로 대치됩니다. C·D 행은 **C만으로 다시 만든** 사전·중앙값으로 대치됩니다([run_weather_model_comparison.py](../notebooks/run_weather_model_comparison.py)의 `build_pair`, 222행). 따라서 같은 항공편이라도 B에서의 대치 결과와 D에서의 대치 결과가 다를 수 있습니다.

### 1.2 Airline: 같은 집단 안의 원래 결측 = 복원 + 잔여

Airline은 `Carrier_Code(IATA) → Airline` 방향으로만 채웁니다. P4·P6 계열은 `bidirectional=False`입니다. 잔여 결측의 원인은 세 가지로 나눴습니다.

- 코드 결측: 그 행의 `Carrier_Code(IATA)`도 비어 있음
- 코드 미관측: 해당 코드에 항공사명이 관측된 적이 없음
- 코드 모호: 해당 코드에 둘 이상의 항공사명이 관측됨

**현행 clean 규칙(`conflict="unique"`, P4_clean·P6_clean)**

**과거 규칙(`conflict="first"`, P4·P6_fixed 등)**: 비교용

| 집단 | 원래 결측 | 복원 | 잔여 결측(전부 코드 결측) | clean보다 더 채운 행 |

## 2. 피드백 3: 시각 복원 규칙

코드: [src/features.py](../src/features.py)의 `parse_hhmm`(199~220행), `build_time_features`(223~262행), `restore_time_missing`(265~341행). 호출 순서는 [rerun_all_phases.py](../rerun_all_phases.py)의 `build_features`(308행~)를 따릅니다. 아래 설명은 현재 코드를 그대로 옮긴 것이며 동작을 바꾸지 않았습니다.

### 2.1 노선 키는 방향이 있다

`Route = Origin_Airport + "_" + Destination_Airport`(`build_features` 322행)입니다. `A_B`와 `B_A`는 **다른 노선**이며 중앙값도 따로 계산합니다. 이 키는 공항명만 쓰며 항공사·시간대·연도는 포함하지 않습니다.

### 2.2 유효 시각차의 정의

1. HHMM을 시·분으로 나눕니다. `hour = HHMM // 100`, `minute = HHMM % 100`, 결측·음수는 `-1`입니다. `strict=False`가 기본이므로 `2400`도 `hour=24, minute=0`으로 유효하게 취급됩니다.
2. 두 시각이 **모두** 유효(`hour ≥ 0`)일 때만 시각차를 계산합니다.
   `gap = (Arr_Hour·60 + Arr_Minute) − (Dep_Hour·60 + Dep_Minute)`, 단 `도착 < 출발`이면 `+1440`(`midnight_wrap=True`).
   예: 23:00 출발, 01:00 도착이면 `60 − 1380 + 1440 = 120`.
3. 따라서 계산된 시각차는 항상 0 이상입니다. 도착 시계가 출발 시계와 같으면 0이 됩니다. 시각차가 비정상적으로 큰 행을 자르는 상한은 없습니다.

### 2.3 시각차 0의 처리: 중앙값 계산과 비율 피처는 규칙이 다르다

- **중앙값 계산(복원):** 0은 유효한 값으로 **포함됩니다**. `groupby(...).transform("median")`은 NaN만 제외합니다. A에는 유효 시각차 0인 행이 370개 있으며, 모두 노선 중앙값 계산에 참여합니다.
- **비율 피처(`Distance_Per_Local_Minute`, safe 모드):** 유한한 **양수** 시각차일 때만 나눕니다. 0은 NaN과 `_Missing=1`, `Local_Time_Gap_Zero=1`로 표시합니다([`build_speed_features`](../src/features.py) 455~473행). P6_clean의 비율 결측 370행이 이 규칙에서 나옵니다([비교 CSV](../output/preprocessing_clean_comparison.csv)).
- 실제 데이터에서 중앙값으로 **채운** 시각차가 0이 된 행은 없습니다(JSON `restored_value_zero = 0`). 그러므로 비율 결측 370행은 모두 원래부터 관측된 0분 행입니다.

### 2.4 시각차 대치 순서: 노선 중앙값 → (노선 대치 후) 전역 중앙값

```
gap_route   = 같은 Route의 유효 gap 중앙값          # 유효 gap이 하나도 없는 노선은 NaN
gap         = gap.fillna(gap_route)
global_med  = gap.median()                           # ← 노선 대치가 끝난 열의 중앙값
gap         = gap.fillna(global_med)
```

전역 중앙값은 **관측값만의 중앙값이 아닙니다.** 노선 중앙값으로 채운 값까지 포함한 열의 중앙값입니다(306행). 실제 A에서는 관측값만의 중앙값 113분, 노선 대치 후 중앙값 112분이었습니다. 코드는 **112분**을 사용합니다. 전역 중앙값은 유효 시각차가 없는 노선의 행에만 쓰이며, A에서 36행, B에서 11행입니다.

### 2.5 한쪽 시각 복원(`% 1440`)과 양쪽 결측

두 마스크는 원래 값 기준으로 미리 계산하므로 서로 겹치지 않고 순서에도 의존하지 않습니다(320~321행).

- 도착만 결측: `Arr = (Dep_Hour·60 + Dep_Minute + gap) % 1440`, 이어서 `Arr_Hour = Arr // 60`, `Arr_Minute = Arr % 60`
- 출발만 결측: `Dep = (Arr_Hour·60 + Arr_Minute − gap) % 1440`(Python `%`는 음수를 0~1439로 돌립니다)
- 이 시점의 `gap`은 그 행에서 관측된 값이 아닙니다. 한쪽 시각이 없으므로 **항상 노선 또는 전역 중앙값으로 대치된 값**입니다.
- **양쪽 결측:** 시각차는 중앙값으로 채워지지만 기준이 될 시각이 없어 `Dep_Hour = Arr_Hour = -1`이 남습니다. 이후 Sin/Cos는 NaN(P6_clean, `missing="nan"`) 또는 정오(P6_fixed, `missing="noon"`)가 됩니다. Traffic은 NaN과 결측 플래그로 남습니다.
- 복원된 시각은 **정수 분까지 추정된 값**이며 관측 사실이 아닙니다. P*_clean은 `*_Originally_Missing` 플래그로 이 이력을 보존합니다.

### 2.6 계산 예

아래 예는 [테스트](../tests/test_feedback_missing_audit.py)의 `test_time_restoration_worked_example`과 같은 데이터이며, 실제 `restore_time_missing`으로 검증했습니다.

| 행 | 노선 | 출발 | 도착 | 원래 gap | 처리 | 결과 |
|---|---|---|---|---:|---|---|
| r0 | A_B | 10:00 | 11:40 | 100 | 관측 | — |
| r1 | A_B | 12:00 | 12:00 | 0 | 관측(중앙값에 포함) | — |
| r2 | A_B | 08:00 | 10:10 | 130 | 관측 | — |
| r3 | A_B | 23:30 | 결측 | NaN | 노선 중앙값 100 → `(1410+100) % 1440 = 70` | 도착 **01:10** |
| r4 | A_B | 결측 | 00:40 | NaN | 노선 중앙값 100 → `(40−100) % 1440 = 1380` | 출발 **23:00** |
| r5 | A_B | 결측 | 결측 | NaN | gap만 100 | 시각은 **계속 결측(-1)** |
| r6 | C_D | 09:00 | 결측 | NaN | C_D에 유효 gap 없음 → 전역 중앙값 | 아래 참고 |
| r7 | E_F | 01:00 | 06:00 | 300 | 관측 | — |

- A_B의 노선 중앙값은 {100, 0, 130}의 중앙값인 **100**입니다. 0을 빼면 115가 되므로 0이 결과를 바꿉니다.
- 관측값만의 전역 중앙값은 {100, 0, 130, 300} → **115**입니다. 코드가 쓰는 노선 대치 후 전역 중앙값은 {0, 100, 100, 100, 100, 130, 300} → **100**입니다. 따라서 r6의 도착은 09:00 + 100분 = **10:40**입니다.
- 이 예의 집계: 출발 원래 결측 2 = 복원 1 + 잔여 1, 도착 3 = 2 + 1, 시각차 4 = 노선 3 + 전역 1 + 잔여 0.

### 2.7 현지 시각차가 실제 비행시간이 아닌 이유

- 원본의 출발·도착 예정 시각은 **각 공항의 현지 시계**로 적혀 있습니다. 시간대가 다른 공항 사이에서는 시차만큼 값이 어긋납니다(동쪽으로 가면 커지고 서쪽으로 가면 작아집니다). 이 코드는 시간대를 보정하지 않습니다.
- `+1440`은 "도착이 출발 후 24시간 안"이라는 가정입니다. 날짜가 바뀌었는지는 확인하지 않습니다.
- 예정 시각이므로 실제 운항 시간도 아닙니다. 그래서 clean 경로는 이 값을 `Local_Time_Gap_Minutes`, 비율은 `Distance_Per_Local_Minute`라고 부릅니다. 복원식의 `gap`도 같은 한계를 지닌 **같은 노선의 전형적인 현지 시계 차이**일 뿐입니다.
- 이 문서는 공항별 시간대를 대조해 오차 크기를 측정하지 않았습니다(**미확인**).

## 3. 피드백 4: Traffic의 의미와 집계 경계

코드: [`build_traffic_features`](../src/features.py)(344~410행), 호출은 `build_features`에서 **시각 복원 다음**(342행)입니다. Traffic은 P6 계열에서만 생성됩니다.

### 3.1 정의

행 `i`의 출발 측 값은 다음과 같습니다.

```
Origin_Traffic_i = |{ j ∈ 묶음 : Month_j = Month_i, Day_of_Month_j = Day_of_Month_i,
                                 Origin_Airport_j = Origin_Airport_i, Dep_Hour_j = Dep_Hour_i,
                                 Dep_Hour_j ≠ -1 }|
```

도착 측(`Dest_Traffic`)은 `Destination_Airport`, `Arr_Hour`로 같은 방식입니다. 구현은 `groupby(keys).transform("size")`입니다.

### 3.3 어느 묶음을 집계했나

| 실험 | 집계 묶음 | 평가 집단 |
|---|---|---|
| 전처리 10조건 비교, OOF 진단(P6_*) | **A: 원본 전체 1,000,000행** | B 255,001 |
| 날씨 사용/미사용 비교(P6_clean 기반) | **C: 날짜 채택 706,759행**(`build_pair`가 채택 행만 넘김) | D 180,332 |

같은 D 180,332행이라도 두 묶음에서 Traffic 값이 다릅니다. 출발 측 기준으로 93,792행은 같고 86,540행은 A에서 더 크며, A에서 더 작은 행은 0입니다. 중앙값은 A 3, C 2입니다(`traffic_bundle_comparison_labeled_attributed`). C는 A의 부분집합이므로 C의 값이 더 클 수 없습니다. 그러므로 두 실험의 "Traffic"은 같은 이름의 **다른 피처 값**입니다.

### 3.4 Traffic이 아닌 것

`Traffic`은 **주어진 입력 표본 안에서, 연도를 구분하지 않은 월·일·공항·시간대별 레코드 수**입니다. 다음과 같이 해석하면 안 됩니다.

- 실제 공항 전체 운항량이나 혼잡도. 표본에 없는 항공편은 세지 않고, 연도가 섞입니다.
- 예측 시점에 확보할 수 있는 운항량. 같은 묶음 전체(미래 행 포함)를 한 번에 셉니다. 예측 시점에 어떤 운항 계획 자료를 쓸 수 있는지는 정의되지 않았습니다. [데이터 사용 계약](../output/pipeline_data_contract.md)도 Traffic을 "표본 내 행 수 proxy", 출처 계약 확정 전 제외 후보로 둡니다.

### 4.2 이 집단의 피처 상태

즉 시간대 정보가 전혀 없는 상태로 학습·평가된 집단입니다.

### 4.3 날씨 평가 집단에서 빠지는 근거

- 날짜 귀속의 대조 키 9개에 두 예정 시각이 포함됩니다([verify_bts_marketing.py](../notebooks/verify_bts_marketing.py) 24~26행 `KEYS`).   - 3,031행 중 날짜 채택 **0행**, 날씨 평가 집단(D 180,332) 포함 **0행**
  - 상태 내역은 `missing_key_single_candidate_year` 2,750, `missing_key_multi_candidate_year` 280, `missing_key_checked_no_candidate` 1입니다.
