## 0. 표지와 먼저 읽는 결론: 두 종류의 개선을 구분한다

이 프로젝트에는 서로 다른 질문이 있습니다.

1. **기존 입력을 더 타당하게 처리하면 성능도 좋아지는가?** 모호한 항공사 대치, 잘못된 시간 해석, 결측 표현을 수정했습니다. 이 비교에서는 Macro F1 향상을 확인하지 못했습니다.
2. **기존 입력에 없던 정보를 더하면 성능이 좋아지는가?** 출발·도착 공항 날씨를 추가했습니다. 같은 평가행·분할·선택 절차를 사용한 비교에서는 세 지표가 세 시드 모두 개선됐습니다.

첫 질문은 **정보를 표현하는 방법**, 두 번째는 **입력 정보의 추가**에 관한 것입니다. 타당한 전처리라도 데이터가 가진 예측 정보 자체를 크게 늘리지 않을 수 있습니다. 따라서 “전처리 수정은 실패했다”나 “깨끗해졌으니 정확도도 올랐다” 모두 결과를 지나치게 단순화합니다.

## 1. README 01 / 출발점: 무엇을 예측하고 무엇으로 평가하나

### 1.1 예측 단위와 정답

한 행의 `Delay`를 `Not_Delayed=0`, `Delayed=1`로 분류합니다. **예측 단위는 CSV 한 행**입니다. ID가 유일하다는 사실만으로 모든 행이 서로 다른 실제 운항편이라고 단정할 수는 없습니다.

`Delay`가 비어 있는 행은 **정답을 모르는 미라벨**입니다. 이것을 0으로 채우면 정답이 없는 항공편을 정상이라고 만들어 버립니다. 미라벨 입력이 비타깃 집계에 쓰일 수 있다는 것과 미라벨에 정답을 부여해 지도학습한다는 것은 다릅니다. 아래 최종 날씨 비교는 P5 유사 라벨 실험이 아닙니다.

또한 코드가 받은 `Delay`를 사용한다는 사실과 원천 라벨의 운항상 정의를 검증했다는 사실은 다릅니다. **이 해설은 “15분 이상이면 지연” 같은 별도 기준을 새로 가정하지 않습니다.**

### 1.2 지표 세 개가 답하는 질문

지연을 양성으로 두면 TP는 잡아낸 지연, FN은 놓친 지연, FP는 정상인데 지연이라고 한 경우, TN은 정상으로 맞힌 경우입니다.

- `Precision = TP / (TP + FP)`: 지연이라고 경고한 것 중 실제 지연의 비율.
- `Recall = TP / (TP + FN)`: 실제 지연 중 잡아낸 비율.
- `클래스 F1 = 2 × Precision × Recall / (Precision + Recall)`: 둘을 조화평균한 값. 위처럼 지연을 양성으로 두면 **Delayed F1**(지연 클래스 F1)이고, 정상을 양성으로 두고 같은 식을 쓰면 Not_Delayed F1입니다.
- `Macro F1 = (정상 클래스 F1 + 지연 클래스 F1) / 2`: 두 클래스에 같은 비중을 줍니다. **지연 클래스 F1만도 아니고 정확도도 아닙니다.**

정상 라벨이 약 82.35%이므로 모두 정상이라고 해도 정확도는 높아 보일 수 있습니다. Macro F1은 소수인 지연 클래스를 무시한 모델에 다른 관점의 평가를 제공합니다. 그렇다고 Macro F1만으로 실제 운영 비용까지 판단할 수 있는 것은 아닙니다.

`LogLoss = −평균[y·log(p) + (1−y)·log(1−p)]`입니다. 정답 확률을 높게 준 예측은 덜 벌하고, 틀린 예측을 확신하면 크게 벌합니다. 확률 0.51과 0.99가 둘 다 “지연” 판정이더라도 정답이 정상이라면 후자가 더 나쁜 확률 예측입니다.

ROC-AUC는 지연 항공편을 정상 항공편보다 더 높은 위험 순위에 두는 능력을 봅니다. **0.672936은 67.29%의 항공편을 맞혔다는 뜻이 아닙니다.** 특정 임계값에서의 재현율·오경보율도 별도로 봐야 합니다.

### 1.3 확률과 분류 임계값

모델이 출력하는 `p`는 지연 확률이고, `p >= 임계값`이면 지연으로 분류합니다. 임계값을 낮추면 일반적으로 더 많은 경고를 내므로 놓치는 지연과 오경보의 균형이 바뀝니다. 현재 절차는 **내부 데이터의 Macro F1**로 임계값을 고릅니다. 비용 최적화나 운영상 최적값을 입증한 임계값은 아닙니다.

**짧게 말하면:** “Macro F1은 두 클래스를 함께 분류하는 능력, LogLoss는 확률의 품질, AUC는 위험 순위를 봅니다. 한 지표의 개선을 다른 지표나 실제 운영 효과로 바꾸어 말하지 않았습니다.”

## 2. README 02 / 데이터 명세: 분모가 바뀌는 이유

### 2.1 네 숫자의 관계

| 집단 | 행 수 | 의미 |
|---|---:|---|
| 원본 전체 | 1,000,000 | 라벨 유무와 날짜 확정 여부를 모두 포함 |
| 원본 중 라벨 있음 | 255,001 | 기존 전처리·보정 비교의 평가 집단; 지연 45,000 |
| 원본 중 날짜 귀속 채택 | 706,759 | 라벨 유무와 무관하게 날씨 결합을 시도한 집단 |
| 날짜 귀속 채택 ∩ 라벨 있음 | 180,332 | 최종 날씨 비교의 평가 집단; 지연 31,805 |

**255,001 → 706,759 → 180,332로 차례로 줄인 것이 아닙니다.** 라벨 유무와 날짜 귀속은 서로 다른 조건이며, 마지막 수는 두 조건의 교집합입니다. 706,759행 중 미라벨은 526,427행입니다. 180,332행 중 정상은 148,527행이고 지연율은 약 17.6369%입니다.

기존 255,001행의 P6_clean 점수 0.575685와 새 180,332행의 날씨 사용 점수 0.598945를 바로 빼면 **날씨 효과와 집단 변화가 섞입니다**. 그래서 새 집단에서 날씨 미사용 조건도 다시 학습해 0.573910과 비교했습니다.

### 2.2 연도는 왜 필요했나

월·일만으로는 특정 날짜의 날씨를 조회할 수 없습니다. 내부 달력 패턴은 실제 달력과 부합하는 신호를 주지만, 같은 요일 배치를 가진 여러 연도를 구분하지 못합니다. 이후 BTS 운항 자료의 2018·2019년 12개월과 대조했습니다.

대조 키는 **기체번호, 출발·도착 공항, 월·일, 거리, 운항사 DOT ID, 출발·도착 예정 시각**의 9개입니다. `Delay`, 실제 지연, 모델 예측, 날씨를 날짜 선택에 사용하지 않았습니다. 9개가 관측되어 있고 후보 연도가 하나인 행만 날짜를 채택합니다.

키가 빠지면 남은 조건을 우연히 만족하는 후보가 하나일 수 있습니다. 그래서 **결측 키의 단일 후보 291,308행은 확정하지 않습니다**. 이 상태의 단일 후보는 남은 키로 맞는 BTS **행 하나**라는 뜻이며, 완전 지문의 단일 후보 **연도**와 정의도 다릅니다.

### 2.3 그림 1: 날짜 귀속 누적 막대

[날짜 귀속 그림](../assets/readme/date_attribution.svg)은 원본 100만 행을 세 부분으로 나눕니다.

1. 채택 706,759행: 완전한 키 + 단일 후보 연도.
2. 보류 291,308행: 결측 키 + BTS 후보 행 하나.
3. 기타 보류 1,933행: 완전 키 복수 연도 141 + 완전 키 후보 없음 417 + 결측 키 복수 후보 1,210 + 결측 키 후보 없음 165.

합은 1,000,000입니다. 색의 면적은 모델 성능이나 라벨 비율이 아니라 **날짜 판정 상태별 행 수**입니다. 전체 보류는 293,241행이며, “아직 검사하지 않은 29%”라는 표현은 틀립니다.

### 2.4 가까운 분포가 대표성을 보장하지는 않는다

라벨·미라벨의 월·공항·항공사 주변분포가 비슷해도 라벨이 무작위로 붙었다고 증명할 수는 없습니다. 날짜 채택 집단에는 필요한 예정 시각 등이 관측된 행이 선택됩니다. 따라서 두 집단에서 성능이 같을 것이라는 주장이나 미라벨·미래 항공편에 대한 일반화는 별도 검증이 필요합니다.

**짧게 말하면:** “100만 행 모두가 정답을 가진 것은 아니고, 모두에 신뢰할 날짜가 있는 것도 아닙니다. 날짜와 정답을 함께 확인한 180,332행을 고정해서 날씨 유무를 비교했습니다.”

## 3. README 03 / 정비 기록: 결측을 채우지 않는 것도 판단이다

### 3.1 항공사 대치: “처음 나온 값”의 문제

같은 IATA 코드에 여러 운항사 이름이 대응할 수 있습니다. 판매 항공사와 실제 운항사는 역할이 다르기 때문입니다. 기존의 첫 관측값 대치는 어떤 행이 먼저 오느냐에 따라 다른 이름을 채웠습니다.

수정은 **대치 이전에 관측된 쌍**에서 대응이 하나인 경우만 사전을 만드는 방식입니다. 관측된 원래 이름은 보존하고, 모호하면 결측을 남깁니다. 항공사명 대치는 97,056건에서 30,608건으로 줄었고, 66,448건의 모호한 채우기를 중단했습니다. 원본 순서를 뒤집었을 때 값이 바뀌던 27,536행은 수정 후 0행이었습니다.

이 검사는 **순서 독립성**을 확인합니다. 관측상 유일한 대응이 외부 원천의 진실이라는 보증까지 하지는 않습니다.

### 3.2 시간차: 계산 가능하다고 물리적 비행시간은 아니다

HHMM은 100진수 시간이 아닙니다. 예를 들어 0130은 130분이 아니라 90분입니다. 시·분을 분 단위로 바꾸고 도착 시계가 더 작으면 1,440분을 더하는 현지 시각차를 만듭니다.

그러나 출발·도착 공항의 시간대가 다르면 이 차이는 실제 경과시간과 다릅니다. 그래서 `Estimated_Duration`을 `Local_Time_Gap_Minutes`로, 거리/시간차를 `Distance_Per_Local_Minute`로 명확히 표현했습니다. **계산값 581도 실제 항공기 속도가 아닙니다.**

기존에는 분모에 0.00001을 더했기 때문에 0분에 가까운 값에서 비율이 폭증했습니다. 수정은 유한한 양수 시간차, 유한한 비음수 거리일 때만 나누고 나머지는 NaN과 표시값으로 둡니다. 최댓값이 75,800,000에서 581로 바뀌었지만 임의 상한으로 자른 것은 아닙니다. 0분 370행도 삭제하지 않았습니다.

### 3.3 시간 복원: 추정과 관측을 구별한다

P6은 노선 중앙값, 없으면 전역 중앙값으로 시간차를 대치하고 한쪽 시각이 있으면 반대쪽을 추정합니다. 양쪽 시각이 없다고 실제 출발 시각을 알아낼 수는 없습니다.

- **원래 결측 표시값:** 입력에서 없었던 값인지 기록합니다.
- **복원 후 결측 표시값:** 복원해도 여전히 시각을 모르는지 기록합니다.
- **복원값:** 중앙값 규칙으로 추정한 값입니다. 관측 사실로 승격되지 않습니다.

원래 결측이었다가 복원된 행은 현재 값이 존재해도 불확실성의 이력이 남습니다. 날씨의 예측 시점을 만들 때 추정한 시각을 실제 관측 예정 시각인 것처럼 사용해서는 안 됩니다.

### 3.4 원형 시각과 Traffic

출발 시간을 `sin(2πh/24)`, `cos(2πh/24)`로 나타내면 23시와 0시가 이어지는 하루의 주기를 표현할 수 있습니다. 두 좌표를 함께 쓰면 같은 sin 값을 가진 서로 다른 시간을 구분할 수 있습니다. 이것이 성능 향상을 자동 보장하는 것은 아닙니다.

이전 P6은 미상 시각을 정오로 바꿔 원형 좌표를 만들었습니다. P6_clean은 11,688행을 NaN으로 두어 실제 정오와 구별합니다.

`Traffic`은 월·일·공항·시간대별 **입력 표본의 행 수**입니다. 실제 공항 전체 교통량, 활주로 점유율, 관제 혼잡도와 동일하지 않습니다. 연도 누락 상태에서 월·일로 집계하던 입력이라는 한계도 기억해야 합니다. 미상 시간대를 하나의 거대한 혼잡 시간대로 취급하지 않도록 집계에서 제외합니다.

### 3.5 범주형과 타깃 인코딩(TE)

공항·항공사 같은 원본 범주형을 유지하면서, 그 범주의 지연 빈도를 평활한 TE를 추가합니다.

`TE = (n × 범주 내 지연율 + m × 학습 집단 지연율) / (n + m)`

여기서 n은 해당 범주의 학습 표본 수이고 m은 전역 평균 쪽으로 당기는 강도입니다. 현행 러너의 m은 20입니다. 표본이 적은 범주의 극단적인 비율을 완화하고, 학습에 없던 범주는 학습 집단 평균으로 처리합니다. **정답을 사용하는 변환**이므로 어떤 라벨로 만들었는지가 핵심입니다. 분할 경계는 다음 절에서 설명합니다.

**짧게 말하면:** “결측률을 낮추는 것보다 관측값·추정값·모르는 값을 구별했습니다. 잘못된 의미를 가진 입력을 바로잡은 뒤, 성능은 별도의 비교로 판단했습니다.”

근거: [전처리 구현·전수 검사 기록](../output/preprocessing_clean_implementation.md), [실제 대치 예시](../output/current_imputation_examples.csv), [피처 함수](../src/features.py), [조건 정의와 피처 생성](../rerun_all_phases.py).

## 4. README 04 / 평가의 경계: 정답을 보고 고른 모델을 같은 답안으로 채점하지 않는다

### 4.1 분석 흐름 그림

[분석 여정 그림](../assets/readme/analysis_journey.svg)은 원본에서 두 경로가 갈라졌다가 합쳐지는 구조입니다. 한쪽은 전처리의 의미와 성능을 확인하고, 다른 쪽은 날짜를 귀속해 외부 날씨를 연결합니다. 마지막에 **P6_clean + 고정된 새 평가 집단**에서 날씨 유무를 비교합니다. 앞 단계의 성능을 그대로 이어 붙인 상승 곡선이 아닙니다.

### 4.2 평가 경계 그림: 외부 5분할 안에 내부 holdout이 있다

[평가 경계 그림](../assets/readme/evaluation_boundary.svg)을 한 외부 fold 기준으로 읽으면 다음과 같습니다.

1. 라벨 집단을 클래스 비율을 고려해 5분할합니다. 20%는 `outer-valid`로 남겨 최종 채점만 합니다.
2. 남은 80%인 `outer-train`을 다시 80:20으로 나눕니다. 전체 기준 약 64%가 `inner-train`, 약 16%가 `inner-holdout`입니다.
3. TE를 **이 내부 분할 이후** 만듭니다. inner-holdout과 outer-valid의 TE는 inner-train 라벨에서만 계산합니다. inner-train 자체의 TE도 내부 교차 인코딩으로 자기 정답이 직접 들어가지 않게 합니다.
4. 트리 수 `[10, 25, 50, 75, 100, 150, 300, 600]`를 각각 학습하고 inner-holdout LogLoss가 최소인 모델을 선택합니다.
5. 선택된 모델의 inner-holdout 확률로 0.10~0.70, 0.01 간격의 임계값 중 Macro F1이 최대인 것을 선택합니다.
6. **선택된 모델을 그대로** outer-valid에 적용합니다. 현재 구현은 선택 후 outer-train 80% 전체에 다시 적합하는 방식이 아닙니다.
7. 5개의 외부 검증 예측을 합쳐 모든 평가행이 한 번씩 채점되도록 합니다. 이것이 해당 시드의 OOF 결과입니다.
8. 시드 42·1·7로 반복하고 **시드별 pooled OOF 지표**의 평균과 표본 SD를 구합니다.

Macro F1은 비선형이므로 “fold별 Macro F1의 단순 평균”과 “전체 OOF 예측을 합쳐 계산한 Macro F1”이 일반적으로 같지 않습니다. 이 저장소는 후자입니다. 각 행의 이진 판정에는 그 행이 속한 외부 fold의 **내부 선택 임계값**을 씁니다. 기록의 `deployment_threshold`는 fold 임계값 중앙값 요약이며 모든 OOF 행을 그 값 하나로 다시 채점한 점수와 혼동하면 안 됩니다.

### 4.3 왜 early stopping 대신 고정 후보를 비교했나

현재 `run_fold_nested_grid`는 각 후보 트리 수까지 학습하고 내부 LogLoss로 고릅니다. 조기 종료 콜백과 `scale_pos_weight`는 이 경로에서 사용하지 않습니다. 과거의 early stopping 문제와 사전 TE의 내부 라벨 유입을 구별하고, 선택 절차를 명시적으로 고정한 것입니다.

**파일을 읽을 때의 함정:** 저장된 protocol에는 호환용 `inner_early_stopping=true`, `stopping_rounds=40`이 보일 수 있습니다. 이 필드만으로 실제 조기 종료를 했다고 해석하면 안 됩니다. 최종 날씨 러너는 `run_fold_nested_grid`를 호출하며, 그 함수는 callbacks를 제거하고 트리 수 후보를 직접 비교합니다. 실행 경로·선택된 트리 수·grid_scores를 함께 확인해야 합니다.

### 4.4 “같은 조건”은 같은 최종 트리 수라는 뜻이 아니다

날씨 off/on은 같은 행·시드·외부 fold, 같은 모델 계열과 후보·선택 규칙을 사용합니다. **각 조건에 가장 적합한 트리 수·임계값은 내부에서 독립적으로 고릅니다.** 실제 off의 선택 트리는 모두 50, on은 75·100·150 중 선택됐습니다. 따라서 이 실험은 “완전히 동일한 학습 모델에 열만 꽂은 효과”보다 **같은 선택 절차에서 날씨 입력을 허용한 파이프라인의 성능 차이**를 평가합니다.

### 4.5 남는 경계: 비타깃 입력 묶음은 분할 전에도 사용한다

라벨 누수를 막았다고 미래 운영까지 검증된 것은 아닙니다. 코드 대응 사전·노선 중앙값·Traffic·범주 목록은 입력 묶음의 비타깃 정보를 사용합니다. 기존 전처리 실험은 원본 100만 행 묶음, 최종 날씨 러너의 `build_pair`는 날짜 채택 706,759행 묶음을 전처리합니다. 그 뒤 각각 라벨 집단을 분리합니다.

이는 **고정된 입력 묶음을 가진 정적 실험**의 계약입니다. 미래 예측에서는 당시 알 수 있는 운항계획을 확보하고, 학습에서 만든 통계를 저장해 새 행에는 적용만 해야 합니다. 무작위 층화 분할은 시간 순서로 완전히 미래를 남긴 테스트도 아닙니다.

**짧게 말하면:** “모델과 임계값을 고르는 내부 데이터와 최종 채점용 외부 데이터를 나눴습니다. 다만 전체 입력 묶음을 활용하는 가정이 남아 있어 미래 운영 성능으로 확대하지 않았습니다.”

근거: [CV 구현](../src/cv.py), [TE 구현](../src/features.py), [날씨 비교 러너](../notebooks/run_weather_model_comparison.py), [정보 사용 계약](../output/pipeline_data_contract.md).

### 5.2 날씨 14개 피처가 무엇인가

출발·도착 각각 다음 7개, 총 14개 수치 피처를 추가했습니다.

- `tmpf`: 기온, 화씨(°F)
- `dwpf`: 이슬점, 화씨(°F). 공기가 냉각되어 포화에 이르는 온도입니다.
- `sknt`: 풍속, knot
- `vsby`: 시정, mile. 얼마나 멀리 볼 수 있는지 나타냅니다.
- `p01i`: 시간 강수 관측, inch. 정확한 누적 구간은 관측소의 직전 시간 강수 초기화 시각에 따라 조금 다를 수 있습니다.
- `age_minutes`: 예측 시점에서 관측이 얼마나 오래되었는지
- `matched`: 관측이 연결됐는지

단위는 [IEM의 변수 설명](https://mesonet.agron.iastate.edu/request/download.phtml)을 기준으로 확인했습니다. 섭씨·m/s·미터·mm로 읽으면 안 됩니다. 피처 추출 코드는 이 수치를 수치형으로 옮기며 단위 변환을 하지 않습니다.

기상값뿐 아니라 **관측의 신선도·가용성도 입력**입니다. 따라서 “기온 때문에 개선됐다” 또는 “날씨의 물리적 효과만 분리했다”는 해석은 할 수 없습니다. 개별 피처의 기여를 이 비교만으로 확정할 수 없습니다.

피처 목록은 모델 점수를 보고 골라낸 것이 아니라 결합 진단과 제출 범위에 따라 미리 고정했습니다. 높은 결측의 gust·snowdepth·wxcodes, 최소 계약에서 중복되는 relh, 추가 범주 확장이 필요한 skyc1, 감사 원문 metar는 제외했습니다. “제외했으니 쓸모없다”는 뜻이 아닙니다.

날씨 수치는 임의 대치하지 않고 LightGBM의 결측 처리를 사용합니다. 관측이 연결되어도 개별 기상값이 결측일 수 있으므로 `matched=1`이 모든 날씨 필드 완비를 뜻하지 않습니다. TE 전 피처는 off 25 / on 39개, TE 추가 후 실행 기록은 off 30 / on 44개입니다. 어느 단계의 피처 수인지 먼저 확인합니다.

### 5.3 그림 3: 동일 집단에서 날씨 off → on

[날씨 비교 그림](../assets/readme/weather_model_comparison.svg)은 180,332행, 3시드 평균입니다. Macro F1과 AUC는 오른쪽으로 커지는 것이 개선이고 LogLoss는 작아지는 것이 개선입니다. **지표별 확대 축이 다르므로 선 길이로 지표 간 개선 크기를 비교하면 안 됩니다.**

| 시드 | Macro F1 차이 | LogLoss 차이 | ROC-AUC 차이 |
|---|---:|---:|---:|
| 42 | +0.025324 | −0.011327 | +0.032011 |
| 1 | +0.024421 | −0.011462 | +0.032291 |
| 7 | +0.025362 | −0.011493 | +0.032650 |

세 시드에서 방향이 일치했습니다. 이는 선택된 이 집단·이 프로토콜에서 개선이 한 분할 운에만 의존하는지 살피는 데 도움이 됩니다. 하지만 같은 데이터를 반복 분할한 것이므로 독립적인 세 데이터셋 검증이 아닙니다.

차이의 SD는 **시드마다 on−off를 먼저 계산한 뒤** 구합니다. on SD에서 off SD를 빼지 않습니다. 표본 SD는 분모가 `3−1`인 시드 간 변동 요약이며, 통계적 유의성 검정이나 미래 성능 신뢰구간이 아닙니다.

지연 재현율 평균은 off 약 34.64%, on 약 35.59%입니다. Macro F1이 개선됐다고 “지연의 대부분을 탐지한다”고 말하면 안 됩니다. 이 값도 내부 Macro F1로 선택한 fold별 임계값에서의 결과이며, 별도 운영 목적의 임계값은 검증하지 않았습니다.

### 5.4 그림 4: 보정의 개선과 분류 성능의 개선

[보정 비교 그림](../assets/readme/calibration_tradeoff.svg)은 날씨 실험이 아닌 **전체 라벨 255,001행의 P6_clean 공유형 보정**입니다.

- Platt: 원래 확률의 logit에 로지스틱 회귀를 적합해 확률을 다시 매핑합니다.
- Isotonic: 확률이 커질수록 보정값이 감소하지 않는 유연한 단조 함수를 적합합니다. 계단형 구간에서 여러 확률이 같은 값이 될 수 있습니다.
- 보정기 적합도 outer-train 내부입니다. 공유형은 내부 선택과 보정에 같은 holdout을 쓰고, 분리형은 그 안을 다시 나누는 대조입니다. 어느 쪽도 outer-valid로 적합하지 않습니다.

`Brier = 평균[(p−y)²]`입니다. `ECE`는 확률을 고정된 10구간으로 나누고 각 구간의 **평균 예측 확률과 실제 지연율의 차이 절댓값**을 행 수로 가중평균합니다. ECE가 작으면 이 구간화 아래에서 평균 확률이 빈도와 가깝다는 뜻입니다. 구간 수·표본 수에 의존합니다. README의 ECE는 원래 비율에 100을 곱한 **%p** 단위입니다.

| P6_clean 공유형 | ECE (%p) | LogLoss | Macro F1 |
|---|---:|---:|---:|
| 없음 | 0.4588 | 0.447577 | 0.575685 |
| Platt | 0.3477 | 0.447519 | 0.575517 |
| Isotonic | 0.1877 | 0.448937 | 0.575248 |

Isotonic은 ECE를 줄였지만 LogLoss는 커졌고 Macro F1 향상도 없었습니다. **구간 평균의 잘 맞음과 개별 확률의 품질·위험 순위·임계값 분류는 같은 목표가 아닙니다.** 계단형 동률에 따른 순위 정보 감소는 관측과 부합하는 해석이며, 모든 변화 원인을 확정한 실험은 아닙니다.

원본 양쪽 시각 결측 3,031행의 P6_clean 지연 재현율은 10.02%였습니다. 이 분모 3,031은 그룹의 전체 라벨 행 수이고, 재현율의 분모는 **그 그룹 안의 실제 지연 행**입니다. 날씨 비교 집단의 수치나 전체 정확도와 혼동하지 않습니다.

**짧게 말하면:** “전처리 비교에서는 Macro F1 개선을 확인하지 못했고, 날씨 비교에서는 같은 180,332행에서 세 지표가 개선됐습니다. 확률 보정은 ECE를 줄여도 지연 탐지 개선으로 이어지지 않았습니다.”

## 6. README 06 / 도착 이후: 미래 정보를 쓰지 않으려면 시각을 두 번 확인한다

### 6.1 예측 시점, 관측 시점, 가용 시점

세 시각을 구분합니다.

- `prediction_at`: 출발 공항 현지 예정 시각을 UTC로 바꾼 뒤 **60분을 뺀 시각**.
- `observed_at`: 날씨가 관측된 시각.
- `available_at`: 예측 시스템에서 이용 가능하다고 놓은 시각. 수신 이력이 없어 `observed_at + 가정한 공개 지연`을 사용합니다.

출발·도착 공항 모두 **동일한 출발 전 prediction_at**을 기준으로 연결합니다. 도착 공항이라고 도착 시점의 미래 날씨를 가져오는 것이 아닙니다. 현재 관측 자료를 쓰며, 예보의 발행 시각·예보 대상 시각을 다루는 계약은 별개입니다.

조건은 `observed_at <= prediction_at`, `available_at <= prediction_at`, 그리고 `prediction_at−observed_at <= 90분`입니다. 관측은 오래전에 일어났더라도 아직 공개되지 않았다는 가정이면 사용할 수 없습니다.

**이해를 위한 가상 예:** 예측 시점이 UTC 12:00이고 11:55 관측에 10분 지연을 가정하면 가용 시점은 12:05이므로 사용할 수 없습니다. 11:45 관측은 11:55에 가용해지고 관측 나이가 15분이라 사용할 수 있습니다. 이는 설명용 예시이며 실제 실행 사례가 아닙니다.

### 6.2 시각 변환의 경계

`2400`은 다음 날 자정으로 변환합니다. 일광절약시간(DST) 전환 때문에 현지 시각이 두 번 존재하거나 존재하지 않으면 `NaT`로 남깁니다. 공항·관측소 매핑이나 시각이 모호하다고 임의 대체하지 않습니다. 미결합 행은 분모에서 남겨 결과가 좋은 행만 고르는 것을 피합니다.

### 6.3 전체 706,759행 결합 결과

10분 가정에서 양쪽 결합 689,457 + 한쪽 결합 1,828 + 미결합 15,474 = 706,759행입니다. 출발 결합 690,361과 도착 결합 690,381은 겹치는 집단이므로 더해서 총 행 수로 쓰면 안 됩니다.

라벨 평가 집단에서는 양쪽 결합 175,939행이지만 **모델 평가 분모는 그대로 180,332행**입니다. 나머지 행이나 개별 날씨 결측값을 이유로 행을 제외하지 않았습니다.

매핑 등급 `confirmed_period`는 IEM 현재 목록의 ID·시간대 문자열·기록 보유 기간을 확인한 상태입니다. 355개 공항의 2018~2019년 물리적 시설 신원과 이전 이력을 모두 역사적으로 입증했다는 뜻이 아닙니다. 추가 조사한 20개 공항도 조회 완료와 역사적 연속성 확인을 구별합니다.

[latency 그림](../assets/readme/weather_latency.svg)의 분모는 **stratafix 300행 중 수집 가능 268행**입니다. 전체 706,759행 결합 표나 180,332행 성능 그래프가 아닙니다.

### 6.5 결론의 세 한계

1. **인과:** 날씨를 입력한 예측기가 더 잘 맞았다는 결과입니다. 날씨가 지연을 얼마나 발생시켰는지, 정책으로 지연을 얼마나 줄일지는 실험하지 않았습니다.

3. **운영 가용성:** 10분은 실측 수신 지연이 아닌 가정입니다. 날씨 결합 규칙을 지켰다는 사실만으로 당시 실제 시스템에서도 받을 수 있었다고 증명할 수 없습니다.

후속으로는 시간 순서의 독립 미래 테스트, 학습/적용 통계 경계, 실제 수신 시각과 운영 비용 기반 평가가 필요합니다. 이는 이번에 완료됐다고 말할 수 있는 범위 밖입니다.

**짧게 말하면:** “도착 공항 날씨도 출발 60분 전에 알 수 있다고 놓은 관측만 사용했습니다. 다만 공개 지연 10분은 가정이므로 실제 운영에서도 같은 정보를 받을 수 있었는지는 후속 검증입니다.”

## 7. README 07 / 정비 매뉴얼: 재현성에도 단계가 있다

### 7.1 무엇을 다시 확인할 수 있는가

| 확인 단계 | 확인하는 것 | 이것만으로 확인하지 못하는 것 |
|---|---|---|
| 문서·그림 검증 | 집계 숫자, 링크, 그림 생성·출처 계약 | 원자료의 진실성, 모델 재학습 결과 |

README에 있는 511개 통과 같은 숫자는 특정 과거 실행의 기록입니다. 현재 커밋의 CI와 같다고 자동 주장하면 안 됩니다. 이 문서의 수치·수식 대조도 모델을 다시 학습한 것은 아닙니다.

### 7.3 수집·복구 도식: 중단을 성공으로 오인하지 않는 설계

README의 수집 도식은 **계획 고정 → 검증된 캐시 확인 → 없으면 예산을 예약하고 요청 → 결과 검증·기록 → 분할 전체가 성공한 경우에만 다음 분할**의 구조입니다.

- 요청 묶음(request group)은 논리적 수집 단위입니다. HTTP 재시도 한 번은 별도의 attempt입니다.
- shard는 기본 50개 요청 묶음씩 저장·재개하는 단위입니다. 전체 수집은 1,317개 요청 묶음, 27개 shard였습니다.
- checkpoint는 “어디까지 했는가”, manifest는 “무엇으로 실행해 무엇이 나왔는가”의 기록입니다.
- fingerprint와 SHA-256은 입력·설정·파일이 바뀌었는지 확인하는 근거입니다. 해시가 맞는다고 데이터 의미까지 참이라는 뜻은 아닙니다.
- 실패·재시도도 예산에 포함합니다. 바이트를 측정할 수 없으면 0으로 간주하지 않고 보수적으로 예약분을 유지합니다.
- fail-closed는 검증되지 않은 상태를 완료로 통과시키지 않는 것입니다. 원자적 교체도 전원 장애까지 포함한 무조건적 영속성 보장은 아닙니다.

최종 캐시·측정 다운로드는 1,093,058,768바이트, 예산 차감은 1,613,058,768바이트였습니다. 차이 520,000,000바이트는 미측정 시도 26건×20MB 예약분입니다. 실제 추가 다운로드량으로 읽으면 안 됩니다. 총 HTTP 시도 1,343건=성공 1,317+실패 26입니다. 별도 감사는 실패를 HTTP 503 25건과 상태 불명 중단 1건으로 정정했습니다. 원본 기록을 지우고 덮어쓴 것이 아닙니다.

**짧게 말하면:** “결과 점수만 남기지 않고 입력·분할·실행 기록을 연결했습니다. 수집 완료, 행별 결합 완료, 모델 평가 완료는 각각 별도로 검증했습니다.”

### 20분 안의 발표로 압축하기

README의 권장 배분은 본문 약 16분+전환·질문 여유 약 3분입니다. 실제 낭독을 측정한 시간은 아니므로 리허설에서 조정합니다.

1. **2분:** 항공편 한 행을 예측한다는 문제와 라벨 경계.
2. **4분:** 모호한 대치를 중단한 예시, 현지 시각차·결측 이력.
3. **3분:** 내부 선택과 외부 채점의 분리. 남는 전체 입력 묶음 가정.
4. **5분:** 전처리 비교의 비개선 → 새 집단에서 날씨 off/on 재비교 → 세 지표 개선.
5. **2분:** 선택 집단·10분 가정·인과/미래 검증의 한계.

추천 마무리: “무엇을 아는지 구분하는 전처리를 먼저 정리했고, 그 위에 날씨 정보를 더했을 때 동일조건 평가에서 예측력이 개선됐습니다. 이 결과의 적용 범위는 날짜가 확인된 집단의 정적 교차검증입니다.”

## 9. README 09 / 상세 기록: 부록을 현재 결론과 연결하는 법

### A. 내부 달력·라벨 대표성·기록 정합성

월·요일·휴일에 따른 행 수 패턴은 연도 추적의 단서였습니다. 같은 요일 배치를 가진 연도는 내부 신호만으로 구분할 수 없으므로 **현재 날짜 채택은 후속 BTS 대조에 근거**합니다. 월별 표본 행 수를 실제 전체 운항량으로 해석하지 않습니다. 주변분포 유사성도 라벨 무작위성의 증명이 아닙니다.

### B. Reporting → Marketing → 12개월 귀속

Reporting 자료에서 11월 완전 지문 5,506행이 처음 맞지 않았지만, Marketing 자료 대조에서는 완전 지문 68,283행이 모두 후보를 얻었습니다. 당시 수록 범위 차이를 살핀 과정입니다. 다만 양쪽 연도에 맞는 12행은 여전히 모호했고 단일 날짜로 채택하지 않았습니다.

**“후보가 생김”과 “연도를 하나로 정함”은 다릅니다.** 원본 `Comair Inc.` 이름만으로 전체 연도를 추정하던 과거 주장은 철회됐습니다. 운항사 식별은 DOT ID를 기준으로 읽습니다. 마스킹 진단에서 오확정이 0이었다는 것도 실제 결측 행의 오류율 0%를 보증하지 않습니다.

### C. 21행·기존 300행·stratafix 300행

21행은 시간대·자정·DST 경계를 확인하는 작은 표본, 기존 300행은 확대 표본, stratafix는 선정 순서 결함을 수정해 **별도로 뽑은** 300행입니다. 합쳐서 621개의 독립 대표 표본이라고 하지 않습니다. stratafix도 341개 층 중 300개만 포함하므로 모든 층을 다 덮지 않습니다.

초기 station-day·병합 구간 수는 수집 규모 산정 단위였습니다. 실제 bulk 요청 1,317개와 단위가 다릅니다. 과거 5.3일 같은 단순 외삽을 최종 실행 시간으로 인용하면 안 됩니다.

### D. OOF·보정·반복 오류 그림 세 장

1. [OOF 확률·결측 진단](../output/baseline_recovery_v2_oof_20260916_v2_diagnostics.png): 전체 점수만 보지 않고 시각 결측 그룹의 Macro F1·지연 재현율·확률 구간을 확인합니다. 선은 시드별 값, 점·오차막대는 평균±표본 SD입니다. 양쪽 시각 결측 그룹의 낮은 재현율을 볼 때 그 집단 크기와 실제 지연 분모를 함께 읽습니다. 작은 고확률 구간을 안정적인 전체 패턴으로 확대하지 않습니다.
2. [보정 전후 오차와 ECE](../output/baseline_recovery_v2_calibration_20260917_reliability.png): 왼쪽의 실제 지연율−예측 확률이 0에 가까우면 해당 구간의 평균 확률이 실제 빈도와 가깝습니다. 오른쪽 점은 시드 ECE, 막대는 평균입니다. 곡선은 3시드 표본수 가중 평균이며 신뢰구간이 아닙니다.
3. [오분류 기술 분석](../output/baseline_recovery_v2_error_profile_20260917.png): 저장된 OOF와 원본을 대조한 기술 분석입니다. 월·공항·항공사 구성, 확률 구간, 반복 FN/FP를 살핍니다. 세 시드 공통 FN은 실제 지연 45,000행 중 24,895행, 공통 FP는 정상 210,001행 중 21,567행입니다. 여러 분할에서도 반복되는 오류가 있다는 관찰이지 항공사나 결측의 인과 효과를 추정한 결과가 아닙니다.

이 세 그림은 기존 전체 라벨 집단의 진단이며 최종 날씨 사용 모델의 오류 분석으로 바꾸어 말하지 않습니다. 환경 간 집계 지표가 일치해도 행별 예측 전부의 동일성을 증명하지는 않습니다.

### E. 수집 예산·재개 계약 수정 이력

실패·재시도·미측정 바이트를 포함하는 회계, 입력 계획 지문, 구조 검사, 명시적 PASS/FAIL이 왜 필요한지 보여 줍니다. 현행 v3는 바뀌면 안 되는 수집 계획과 조정 가능한 누적 총예산을 분리합니다. 상한을 올려도 과거 사용량을 초기화하지 않습니다. 구버전 기록을 현행 계약으로 자동 승격하지 않습니다.

### F. 20개 공항의 관측소 신원

현재 코드가 맞는 것, 관측 프로그램이 연결되는 것, 2018~2019년 시설 연속성이 확인되는 것은 각각 다른 수준의 주장입니다. 예를 들어 COOP 기록이 있다고 ASOS/AWOS 운영기간을 입증한 것은 아닙니다. 메타데이터 편집일도 시설 개장일이 아닙니다. 조사한 대체 ID를 실제 모델 매핑에 자동 반영하지 않았습니다.

### G. 실행 명령과 입력 계약

명령을 복사하기 전에 원본·캐시·해시·코드 버전·기존 출력 존재 여부를 확인해야 합니다. 날짜가 든 실행명은 당시 근거의 식별자이며 새 실험으로 덮어쓰라는 뜻이 아닙니다. `--validate-inputs-only`는 입력 계약 검사이고 전체 학습·결합 완료가 아닙니다. `uv --offline`은 패키지 접근 제한이지 Python 코드의 모든 네트워크를 차단하는 장치가 아닙니다.

### H. 과거 테스트 수와 철회된 해석

테스트 수는 실행 시점별 이력입니다. 일부 스모크 통과를 전체 모델 성능 검증이라고 부르지 않습니다. 초기 early stopping 붕괴 결과를 현재 Phase 순위로 되살리지 않습니다. 새 결론으로 수정된 과거 해석은 철회 상태로 보존합니다.

### I. 초기 로컬 실행 기록

stratafix 수집 당시 “전체 수집을 하지 않았다”는 문장은 그 회차의 범위입니다. 이후 전체 27/27 shard 수집·최종화·706,759행 결합·180,332행 모델 비교까지 완료됐습니다. **기록의 당시 시점과 현재 상태를 분리해 읽는 것**이 이 부록의 핵심입니다.

## 예상 질문과 답변의 핵심

**Q1. 왜 LightGBM인가요?**  
현재 프로젝트는 범주형·수치형·결측을 포함한 표 형식 입력을 LightGBM 이진 분류 경로로 비교했습니다. 핵심은 같은 모델 계열·선택 절차를 유지해 전처리와 정보 추가를 비교하는 것입니다. 다른 모델보다 최고라고 입증한 모델 선택 연구라고 말하지 않습니다.

**Q2. 전처리 후 성능이 그대로면 굳이 수정할 이유가 있나요?**  
행 순서에 따라 항공사명이 바뀌거나 모르는 시각이 정오로 표현되는 문제는 의미·재현성 문제입니다. 그 수정을 유지할 이유와 Macro F1 향상 여부를 구분했습니다.

**Q3. 미라벨이 많은데 왜 다 쓰지 않았나요?**  
정답이 없는 행을 정상으로 만들 수 없습니다. 비타깃 입력 묶음 집계에는 미라벨 입력이 쓰이지만, 최종 점수는 관측된 라벨로 채점합니다. 유사 라벨 P5는 이 최종 비교가 아닙니다.

**Q4. 날씨 결합이 잘된 행만 남겨 점수가 오른 것 아닌가요?**  
두 조건의 평가행은 같은 180,332행이며 날씨 미결합·필드 결측 때문에 제외하지 않았습니다. 다만 날짜 귀속 가능한 집단을 선택한 한계는 남습니다.

**Q5. 왜 도착 공항 날씨를 써도 미래 누수가 아닌가요?**  
두 공항 모두 출발 60분 전이라는 같은 시점까지 가용하다고 놓은 관측만 씁니다. 도착 시점의 미래 관측을 사용하지 않습니다. 실제 공개 지연이 10분이었는지는 검증하지 못했습니다.

**Q6. 10분을 골라서 성능이 가장 좋은 것만 보인 건가요?**  
10분과 14개 피처는 모델 비교 전에 고정했습니다. 0·30·60분은 결합률 민감도만 확인했으며 모델 성능으로 고른 후보가 아닙니다.

**Q7. 세 시드 모두 좋아졌으니 통계적으로 유의한가요?**  
방향의 일관성을 확인한 것입니다. 독립 데이터셋 세 개가 아니며 보고된 SD는 신뢰구간이나 유의성 검정 결과가 아닙니다.

**Q8. Macro F1 0.599면 실서비스에 충분한가요?**  
점수 하나로 판단할 수 없습니다. 놓친 지연·오경보 비용, 운영 임계값, 미래 데이터, 당시 가용 입력이 필요합니다. 현재 날씨 사용 모델의 지연 재현율도 평균 약 35.59%이므로 대부분을 탐지한다고 말할 수 없습니다.

**Q9. ECE가 좋아졌는데 왜 보정 모델을 최종 개선으로 내세우지 않나요?**  
ECE는 확률 구간 평균의 일치이고 Macro F1·LogLoss·순위는 다른 특성입니다. Isotonic은 ECE가 줄면서 LogLoss가 악화됐고 Macro F1 향상도 확인되지 않았습니다.

**Q10. 가장 큰 성과를 한 문장으로 말하면요?**  
“불확실한 입력과 평가 경계를 명시한 뒤, 같은 날짜 확인 집단에서 날씨 정보 추가의 예측 성능 개선을 확인했습니다.”

**Q11. 다음에 딱 하나 더 검증한다면요?**  
미래 일반화가 목적이라면 시간 순서로 남긴 독립 테스트와 그 시점의 입력 가용성 계약부터 확인하는 것이 자연스럽습니다. 이는 이번 결과의 한계에서 도출한 후속 제안이며, 이미 실행한 실험은 아닙니다.
