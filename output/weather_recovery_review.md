# 날씨 활용 재검토 및 재개 준비

작성: 2026-09-16. 원본·기존 진단 문서는 보존했다. 실제 실행과 미확인 사항을 분리한다.

## 결론

**기존 날씨 결합본은 검증되지 않은 입력이다. 그러나 ‘날씨가 예측에 도움이 안 된다’는 결론은 성립하지 않는다.**
기존 실험에는 미검증 연도, UTC/현지시각 미변환, 제한된 공항 범위, 결측 변수,
Phase 6과 다른 시간 복원, 기존 모델의 조기종료 붕괴가 함께 있었다.
날씨 피처 중요도 0이나 과거 성능 하락만으로 날씨의 효용을 판정할 수 없다.

대체 공항 관측자료 수집과 시간 정렬 코드 검증은 완료했다.
**실제 항공편의 연도/원천 날짜는 아직 확인하지 못했다. 따라서 실제 100만 행에 새 날씨를 병합하거나 날씨 모델을 학습하지 않았다.**
이는 데이터 정합성의 차단 조건이며, 승인만으로 해결할 수 있는 문제가 아니다.

## 전처리 노트북에서 Teacher·트리 수·임계값 선택을 하지 않은 이유

이전 노트북의 질문은 ‘어떤 원본 문제에 어떤 전처리를 적용했고 무엇이 달라졌는가’였다.
Teacher는 미라벨 행의 가짜 정답을 생성하는 학습이고, 트리 수는 모델 복잡도 선택,
임계값은 확률을 분류 결정으로 바꾸는 선택이다. 어느 것도 모든 행에 먼저 적용할 단순 변환이 아니다.
세 작업은 검증 경계를 지켜 실행하는 별도 모델 실험에서 다뤄야 한다.
그 때문에 이전 노트북은 실제 전처리/TE 검사까지만 수행했다. 필요가 없다는 뜻도, 구현이 없다는 뜻도 아니다.
당시 전체 Phase 재학습을 별도 단계로 둔 작업 범위도 따랐다.

이번에는 사용자의 후속 요청에 따라 날씨 원천 조사·실수집·안전한 결합 코드·테스트까지 확장했다.
모델 실행 없이도 날씨를 잘못된 시각에 연결하는 문제와 수집 가능성은 직접 검증할 수 있다.

## 2. 시각과 관측 출처의 문제 — 코드/공식 정의 확인

- [DACON 원본 설명](https://dacon.io/competitions/official/236094/data)은 출발·도착 시각을 현지 시각으로 정의한다.
  해당 설명에는 연도 컬럼이 없으며 2022년 운항이라고 확인할 근거를 찾지 못했다.
- [Meteostat 시간 규약](https://dev.meteostat.net/formats)은 UTC다.
  `merge_weather_pipeline.py`는 `Hourly(station_id, start_date, end_date)`를 호출한 뒤
  time의 월·일·시를 현지 항공 시각과 그대로 조인한다. 시간대 인자·변환이 없다.
  뉴욕 12시는 겨울 17 UTC, 여름 16 UTC다. 시간뿐 아니라 날짜 경계도 이동한다.
- 현재 설치된 Hourly의 기본값은 `timezone=None, model=True, flags=False`다.
  코드상 모델 자료를 허용하고 원천 플래그를 저장하지 않는다. **기존 CSV 중 모델값이 몇 행인지는 알 수 없다.**
  현재 설치 버전 확인이 과거 실행 환경의 완전한 증거는 아니므로 과거 전체 자료를 모델값으로 단정하지 않는다.
- `find_flight_year.py`는 검색 URL을 출력할 뿐 날짜를 검증하지 않는다.
- 도착 현지 날짜는 출발의 Month/Day와 같다고 가정할 수 없다. 시간대·자정·날짜 변경을 확인해야 한다.
  단순 시각차로 도착일을 임의 복원해 관측을 붙이지 않는다.

## 4. 실제 대체 수집 시험

[IEM API](https://mesonet.agron.iastate.edu/cgi-bin/request/asos.py?help)의 문서화된 파라미터를 사용했다.
대상은 **2022-12-23 UTC 하루, ATL/JFK/ORD, routine + special**.
이는 연결과 변수 존재 확인을 위한 선택일이며 해당 비행 데이터의 연도로 채택한 것이 아니다.

| 공항 | 보고 수 | 시정 값 있음 | 돌풍 값 있음 | 적설 깊이 값 있음 |
|---|---:|---:|---:|---:|
| ATL | 27 | 27 | 21 | 0 |
| JFK | 39 | 39 | 36 | 0 |
| ORD | 36 | 36 | 36 | 4 |
| 합계 | 102 | 102 | 93 | 4 |

**돌풍을 실제로 받을 수 있다는 점은 확인했다.** 이 표는 연중 수집률이나 기존보다 정확한 예측력을 입증하지 않는다.
돌풍 미보고를 0으로 해석하지 않으며, 적설 깊이와 눈 현상 코드 SN은 서로 다른 변수다.
강수 미량 T를 보존했다. 원문에는 `IEM_GHCNH` 표시가 있는 보고도 있어 모든 행이
최초 송신 METAR 그대로라고 가정하지 않는다. 실제 관측값·원문·원천과 사후 보강 여부를 분리해야 한다.

원본 다운로드: `data/weather_probe/iem_20221223_ATL_ORD_JFK.csv`.
요청 URL·SHA256: `output/weather_review/iem_probe_source.json`.

## 5. 구현과 검증

새 파일 `src/weather.py`:

```python
local_hhmm_to_utc(dates: pd.Series, hhmm: pd.Series, timezone: str) -> pd.Series
join_weather_asof(requests: pd.DataFrame, observations: pd.DataFrame,
                  *, max_age: str = "90min") -> pd.DataFrame
```

- 완전한 현지 날짜를 입력받는다. 연도나 도착일을 만들지 않는다.
- 잘못된 HHMM은 NaT, 2400은 다음 자정, DST 중복/없는 시각은 NaT로 남긴다.
  2400은 변환 함수의 명시적 정책이며 비행 원천과의 규약 일치는 추가 검증 대상이다.
- 시간대 없는 예측/관측 timestamp를 거부한다.
- 관측 시각과 이용 가능 시각을 별도로 받고, 예측 시각까지 이용 가능한 보고만 backward 결합한다.
- 관측의 오래된 정도를 90분으로 제한한다. 90분은 첫 시험의 설정이며 최적값이라고 주장하지 않는다.
- 동일 관측소/이용가능시각의 중복 보고는 조용히 첫 행을 택하지 않고 오류로 거부한다.
- 원본 요청 행수·순서·인덱스를 유지하며 미상 시각/관측소는 미매칭으로 남긴다.
- 마지막으로 이용 가능해진 보고를 선택하는 보수적 정책이다. 뒤늦은 오래된 정정보고가 최신 보고를
  가리는 경우는 upstream에서 버전/유효 관측 상태를 정리해야 한다. 배포 완료 모듈이 아닌 검증된 결합 기초다.

실제 관측 102개 + 공항·정시 기준 72개 시험 요청으로 결과를 확인했다.
**68개 매칭, 미래 이용가능시각 선택 0, 최대 관측 나이 69분**, 실제 비행 행 사용 0.
이 시험만 `available_at = observed_at + 10분`을 가정했다. 당시 수신 이력을 확보한 것이 아니므로
운영 환경의 완전한 시점 일치 검증으로 해석하면 안 된다. 첫 요청은 전날 관측이 없어 미매칭될 수 있다.

`tests/test_weather.py` 6개 신규 구조 테스트와 기존 feature/pipeline 테스트 **총 146개 통과**.
미래 발표 보고 차단, 공항 분리, 오래된 관측 제외, 중복 거부, DST/2400, 행 보존을 검증했다.
학습용 `rerun_all_phases.py`, `src/cv.py`, `src/features.py`는 **이번 작업에서 수정하지 않았다**.

## 6. 정확한 날짜를 구하는 다음 경로와 현재 남은 조건

[BTS 원본 다운로드](https://www.transtats.bts.gov/DL_SelectFields.aspx?QO_fu146_anzr=%5D&gnoyr_VQ=FGJ)는
Year/FlightDate를 제공한다. **대조할 출처는 확인했지만 원본 운항 기록 대조 자체는 아직 수행하지 않았다.**

1. `year_verification_fingerprints.csv`에 월별 20개씩 240개 완전한 지문을 저장했다.
   Tail_Number, 양 공항, 월·일, 두 시각, 거리, DOT 식별자를 쓰며 Delay는 제외했다.
2. 복수 후보 연도의 BTS 월별 원본과 대조한다. DACON의 Estimated 시각이 BTS의 CRS인지 실제 시각인지도
   검증 대상이다. 사전 예측 피처로 사용할 수 있는지도 이 정의에 달려 있다.
3. 한두 항공편이 맞았다고 연도를 확정하지 않는다. 월·항공사·노선에 걸친 일치율,
   복수 연도 중복 후보, 미일치/불일치 비율을 비교한다. 여러 연도의 혼합 가능성도 열어 둔다.
4. 연도와 양 공항 현지 날짜가 확인된 행만 결합한다. 공항→관측소→IANA 시간대 매핑도
   좌표·공항명·해당 기간 운영 이력으로 검증한다. IATA 앞에 K를 무조건 붙이지 않는다.
5. 못 찾은 날짜를 2022년으로 채우지 않는다. 날짜를 끝내 확인할 수 없다면 사건별 날씨는 보류하고,
   월별 기후평년값을 별도 가설로 검토한다. 이를 실제 그날 날씨라고 표현하지 않는다.

현재 공개 설명만으로 연도·날짜를 확정할 수 없었고 로컬에 BTS 원본도 없다.
**새 결합 코드가 준비됐다는 사실과 실제 항공편 결합이 완료됐다는 사실을 구분해야 한다.**

## 7. 재학습 조건과 강사 설명 방향

날짜 확인 후 예상 출발 전 일정 시점(예: 60분 전)을 정의한다. 예측 시점 정의는 성능을 보고 바꾸지 않는다.
양 공항 관측은 같은 cutoff까지의 정보만 사용한다. 도착 때 관측된 미래 날씨를 출발 전 예측에 쓰지 않는다.
도착시간대 날씨는 당시 발행된 예보를 쓰며, 예보 발행·유효시각을 함께 보존한다.

이후 동일한 clean nested CV, 같은 시드/행/시간 복원/TE/임계값 절차에서
날씨 없음 → 출발지 관측 → 양 공항 관측 → 예보 추가를 하나씩 비교한다.
전체 점수와 동일 매칭 부분집합 점수를 둘 다 보고, 결측 플래그만의 효과도 분리한다.
이번 조사에서는 전체 Phase 재실행이나 날씨 성능의 새 수치를 만들지 않았다.

추가로 원 대회는 [공식 페이지](https://dacon.io/competitions/official/236094/data)에 LogLoss로 표시된다.
프로젝트가 Macro F1을 강조하는 것과 원 대회 평가 목적은 구분해 발표해야 한다.
공식 기준이라고 Macro F1만을 소개하지 않으며, 기존 프로젝트 지표 설정은 이번에 임의 변경하지 않았다.

강사님께는 ‘날씨를 넣어봤지만 실패했다’보다 **‘외부 데이터를 결합하려면 연도·시간대·관측소·
